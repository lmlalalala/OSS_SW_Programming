# Inner Source 도입 로드맵

## 목표와 적용 대상

Inner Source는 OSS의 공개적인 협업 방식을 조직 내부 개발에 적용하는 방식이다.
소스를 인터넷에 공개하는 것과는 구분된다. 아래는 실제 조직에서 시행한 결과가 아닌 가상 도입 계획이다.
두 개발팀이 각각 운영하는 지표 수집 스크립트를 공통 DORA 보고 도구로 통합하는 상황을 가정한다.
중복 개발을 줄이고 다른 팀도 Issue와 PR로 개선에 참여하도록 하는 것이 목표다.

## 역할과 운영 원칙

- 후원자: 두 팀의 책임자가 담당하며 기여 시간과 운영 인력을 확보한다.
- 호스트 팀: 공통 도구 운영, 릴리스, 장애 대응을 책임진다.
- Trusted Committer: 호스트 팀의 담당자 2명이 설계와 리뷰·병합을 맡는다.
- 기여 팀: 개선 제안과 PR을 제출하고 관련 검증 결과를 제공한다.

사내 저장소는 승인된 구성원이 검색·열람할 수 있도록 하고, 쓰기·병합 권한은 역할에 따라 제한한다.
기밀·개인정보·비밀키는 공유하지 않고 별도 접근 통제를 적용한다. 외부 배포는 별도의 보안·권리 검토를 거친다.
README, CONTRIBUTING, 행동 강령, 소유자 및 문의 경로를 명시한다.
Issue → 작업 브랜치 → PR → 리뷰 → 병합 → 릴리스의 흐름을 사용하고 중요한 결정은 ADR에 기록한다.
첫 응답은 영업일 2일 이내를 목표로 하며, 지연 시 사유와 예상 일정을 남긴다.

## 8주 실행 계획

| 단계 | 기간 | 담당 | 주요 활동·산출물 | 다음 단계 진입 기준 |
|---|---|---|---|---|
| 준비 | 1~2주 | 후원자·호스트 팀 | 공통 도구 선정, 권한·기밀·의존성 검토, 소유자 지정, 기존 처리 시간 측정 | 두 팀의 참여 합의 및 공유 가능 범위 확정 |
| 기반 구축 | 3~4주 | Trusted Committer | 사내 저장소, 시작 가이드, 기여 규칙, PR 템플릿, 최소 검증 절차 | 다른 팀원이 안내만 보고 실행하고 첫 PR을 제출 |
| 시범 운영 | 5~6주 | 두 팀 | 초보자용 Issue, 교차 팀 PR 2건 이상, 리뷰·ADR 기록, 주간 회고 | 교차 팀 PR 2건 병합 및 첫 응답 목표 준수율 80% 이상 |
| 평가·확대 | 7~8주 | 후원자·호스트 팀 | 지표 비교, 문서 보완, 운영 부담 평가, 추가 팀 온보딩 | 재사용 팀 2개 이상 및 운영 담당자 지속 확보 |

수치는 도입을 평가하기 위한 제안 목표이며 현재 달성 실적이 아니다.

## 측정과 위험 대응

| 지표·위험 | 측정 또는 대응 |
|---|---|
| 팀 간 기여 | 호스트 팀 외 구성원의 PR 제출·병합 수를 주 단위로 집계 |
| 첫 응답 시간 | Issue/PR 생성부터 운영자의 첫 실질 응답까지 영업시간 기준 측정 |
| PR 처리 시간 | 생성부터 병합까지의 중앙값을 도입 전후 비교; 미병합 PR의 대기 기간도 확인 |
| 재사용 | 실제 도구를 사용하는 팀 수와 중복 스크립트 제거 사례 기록 |
| 리뷰 병목 | 담당자 2명과 대체 담당자 지정, 기여 규모를 작게 유지 |
| 참여 저조 | 팀별 기여 시간 확보, 작은 Issue 제공, 기여 결과를 회고에 공유 |
| 품질·보안 | 관련 실행 검증과 리뷰 후 병합, 비밀정보·제3자 라이선스 점검 |

8주 후 목표 미달이면 팀 수를 늘리기보다 문서·리뷰 병목을 개선하고 시범 기간을 연장한다.
이 저장소의 4주차 GitHub Flow 및 5주차 Discussions·Wiki·ADR 체계를 내부 협업의 출발점으로 재사용할 수 있다.

참고: [InnerSource Commons Patterns](https://patterns.innersourcecommons.org/) — 조직별 환경에 맞게 적용한다.
